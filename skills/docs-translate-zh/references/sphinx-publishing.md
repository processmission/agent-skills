# 中文文档镜像、构建与发布

## 目录与范围

保持英文源文不动，中文文章按相对路径镜像；配置、模板、术语和维护工具放在翻译子树。
例如英文文档根为 `docs/`：

```text
docs/
├── index.rst
├── system/
│   └── introduction.rst
└── translations/
    ├── terminology.md
    ├── tools/
    └── zh_CN/
        ├── index.rst
        ├── system/
        │   └── introduction.rst
        ├── _templates/
        ├── _static/
        └── _meta/
```

`zh_CN/` 内不再增加 `docs/`。维护文件命名应避免与原文路径冲突。
文档根之外的手写 RST 可用明确的独立命名空间镜像，并记录原始仓库相对路径；
不能假定它们会自动成为 Sphinx 页面。生成内容及测试夹具应明确列入排除清单。

先查目录和 include 关系，不能将外部手册的入口页误认成手册正文。
例如 Yocto 文档中的 BitBake 介绍不等于 BitBake 仓库中的用户手册；
外部仓库需单独确认来源和任务范围。

## 构建策略

复用项目原有 Sphinx 主题、扩展及生成器，维持英文构建行为。
按项目实际情况选择中文源目录或读取阶段的中文覆盖，不能跨项目硬套扩展。
新增依赖或中文专用扩展尽量通过独立构建入口启用，避免提高正常英文构建的要求。

只发布中文 HTML，英文入口指向匹配版本和路径的官方英文页面。
必要时可构建英文 dummy 库存以验证结构和锚点，不需要发布英文 HTML。
上游没有的 fork 专属页面可链接到同一发布分支保留的英文源文，标明“英文源文”。
不能为每页拼接一个未经核实的官方 URL。

首页、导航、搜索框、页脚及按钮也应中文化；项目介绍、维护说明、官方仓库和
中文维护仓库入口按当前项目事实填写。界面定制放在翻译目录的模板或静态资源中，
不再为新界面翻译引入 PO。

源码生成的 QAPI、`.hx`、kernel-doc、API 参考等保持英文；
翻译手写外围说明。确保不因缺少生成内容而出现空链接或 404。

## 验证不变量

从同一英文基线提取并对比章节数量、层级、顺序，代码块内容、图片 URI 和引用目标。
如果使用覆盖扩展，也验证 include 的中文来源及保存源文功能，避免下载到过期英文。
维护逐文件基线；需要翻译的叙述性字面量采用逐块、精确摘要值的审阅例外。

尽量保留英文规范锚点，保证外部链接稳定。仅向节点追加旧 ID 不够：
隐式标题与显式标签可能争用同一个 ID，需处理所有者和引用重映射。
原始 docutils 隐式标题引用可能在 `doctree-read` 前解析失败，
应使用合适的显式标签或在正确解析阶段处理，不能假设晚期补 ID 能修复所有引用。

使用项目对应的严格构建方式，例如 Sphinx 的 `-W --keep-going`。
不要靠禁用全部警告或静默回退英文来让发布通过。
不完整预览可以单独允许，但必须清楚标识，不能作为完整翻译发布的证据。

构建后检查：

- 本地 HTML 文件链接及 fragment 都可解析。Sphinx 构建成功不能证明原始 HTML 链接有效。
- 中英文 doctree 中的外部 URL 没有因标点、转义或改写意外变化。
- 中文术语、英文原名及标识符均能搜索。索引分词和浏览器查询必须匹配，
  不可只换服务端分词而忽略客户端。使用扩展 API 时核对类型，例如路径参数不能传代码片段。
- 首页、嵌套目录、代码复制、复杂表格、ASCII 图、移动或窄屏页面实际显示正常。
  中文字体可能破坏图表对齐；若需要专门处理，只作用于已确认的说明块，保留复制文本。
- 输出来自当前源文的干净构建，没有旧预览、过期 `_sources` 或英文占位内容。

大型站点链接检查尽量流式提取，避免同时保存所有页面完整 DOM。
回归测试只覆盖确有风险的复用逻辑，例如锚点冲突、代码误改和中文搜索；
不为翻译句子本身编写镜像式测试，也不启动项目的原生软件测试矩阵来验证文档。

## 仅在已授权时配置 GitHub Pages

1. 核对远程归属、请求的基线和发布分支；不要从无关当前分支建立翻译分支。
   保护现有工作区，提交署名遵循当前用户授权及项目规则，不能从旧任务复制身份认证。
2. 构建工作流只安装文档依赖，生成需要的参考资料和中文站点；
   不构建样例固件、系统镜像或全部硬件平台。原生 CI 如需跳过，限定在翻译分支，
   不能全局关闭主线验证。
3. 按项目要求固定依赖，使用可信 Action 版本或提交；
   构建默认只读权限，部署才赋予 Pages 和 OIDC 所需权限。
   PR 只构建，不能把不受信任的 PR 内容直接部署到生产站点。
4. 采用 GitHub Actions 部署源，确认 Pages 环境允许发布分支。
   正确设置仓库子路径、资源 URL 和站点根地址。
   仅在文档版本逻辑需要时获取历史或 tags；不要关闭版本校验来掩盖缺失 tags。
5. 按逻辑拆分提交。修复归入对应变更时，先确认远程历史和授权，
   不自动重写其他人的提交或强推共享分支。
6. 等待**所推送提交 SHA** 对应的构建和部署完成，再访问线上首页、深层页面、
   样式脚本、搜索和英文入口。任务启动、制品上传或 HTTP 200 都不等于正常展示。

保留真实部署 URL、运行链接和验证结果；明确说明未完成的人工审阅或外部服务配置。

## 外部服务边界

静态 Pages 不能安全保存客户端 API 密钥。仓库 Secret 仅供获授权的 CI 使用，
把它写入生成的 JS 或 HTML 后就不再是秘密。
第三方助手的官方集成可能限制域名，不能因为 localhost 可用就假设 fork 站点可用。
未经授权不要复用别人的集成、提交凭据或把文档发送给付费翻译服务。
若用户不需要助手，按请求移除；不要为了文档翻译自动扩展成后端服务开发。
