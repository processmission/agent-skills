# 项目术语表与使用规则

具体词条见 [五项目术语附录与扫描工具](term-scan.md)。本页保留决策规则，
附录保存可维护的数据，不在 `SKILL.md` 内堆放词条。

## 落地位置

优先维护项目现有术语表。没有时，在中文维护目录创建 `terminology.md`，
例如 `docs/translations/terminology.md`，随译文一起版本管理。
也可以维护 wiki，但仓库应保存可离线审阅的快照或明确版本链接。
本文件提供规则和模板，不是适用于所有项目的“官方译名词典”。

## 决策顺序

1. 确认词在当前项目、子系统和版本中的含义，而不是直接查通用词典。
2. 优先采用同一含义的项目官方中文译名或规范中的译名，并记录出处。
3. 没有官方译名时，可以采用适合该语境、含义准确且有依据的通行译名；
   明确标为项目约定，不能宣称官方认可。
4. 存在歧义、证据不足或译名可能误导时，保留英文并登记待决事项。
   已有相反约定时先提出冲突，不在不同文章中各自决定。
5. 产品名、工具名、协议缩写和代码标识符通常保留原名。
   是否存在适合使用的官方中文名仍须按具体项目判断。

## 渲染规则

- `bilingual`：每次专业术语出现都使用 `中文（English）`，不只首处。
  标题、表格、链接显示文字也适用。保留英文原名的大小写和拼写以便检索。
- `keep-English`：直接使用英文，不强造中文名，也不写成 `English（English）`。
- 已经是 `中文（English）` 的内容不得再次追加英文括号。
- 普通连接词和一般叙述不属于术语，不把整篇译文改成逐词双语对照。
- 机器解析内容优先保持完整：命令、选项、文件路径、配置项、API 名、URL、
  RST 标签及角色目标不能译写或附加括号。可在其周围的说明文字中解释。
- 链接显示文字和链接目标分开处理；翻译显示文字，不改其目标标识。
- 中文专业术语包含缩写时，在表中明确固定展示形式，避免各章混用全称和缩写。

## 可复制模板

```markdown
# 术语表

适用项目与版本：<项目、分支或版本>
英文基线：<提交或发布版本>

| 英文原名 | 语境/含义 | 策略 | 中文译名 | 固定展示形式 | 依据及版本 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| <English> | <子系统与含义> | keep-English / bilingual | <译名或空> | <完整文本> | <官方文档路径、规范或项目约定及理由> | 待确认 / 已确认 |

## 冲突与待决事项

- <术语>：<不同含义、当前保留方式、需要确认的依据>。
```

“已确认”需有记录支持；若写“人工审定”，必须确实获得人工审阅。
同一个英文词不同含义可以占多行，不按英文键强行合并。

## 示例与反例

以下仅演示决策，不替代项目内的术语确认：

| 场景 | 处理 |
| --- | --- |
| 项目确认将 toolchain 译为工具链 | 正文和标题均使用“工具链（toolchain）” |
| `CONFIG_FOO`、`qemu-system-aarch64` | 原样保留；不改名、不插入括号 |
| QEMU、BitBake | 通常保留产品名称；不要凭发音创造译名 |
| master / slave | 先查该协议或子系统语义；不得机械译为“主人 / 奴隶” |
| `master` 是分支名 | 保留代码字面量 `master`，不按角色术语翻译 |
| 中文译名已附英文 | 复用固定展示形式，避免“工具链（toolchain）（toolchain）” |

## 审阅与检索

逐项检查中文译名是否脱离语境、是否遗漏英文括号，及保留英文策略是否被破坏。
查找可先用 `rg`，但不能全局替换同形多义词，也不能用正则结果代替语义审阅。
抽查生成站点中的中文术语和英文原名都能检索到相关页面；
正文含英文不代表搜索索引、分词和浏览器查询一定正确。
